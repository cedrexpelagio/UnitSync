# UnitSync: ROTC Attendance Management System

A multi-role web system that replaces manual attendance taking and centralizes cadet records. Platoon Leaders record attendance, Battalion S1 and Brigade S1 review and approve it, and Class Presidents monitor their section.

Screen layouts and interface rules are in `UI_DESIGN.md`. Technical rules are in `RULES.md`.

---

## 1. Roles at a Glance

| Role | Scope | Main Purpose |
|---|---|---|
| Admin | Whole system | Approve accounts, manage users, manage training sessions, view audit logs |
| Class President | Own program (for example BSIT, BSCE) | Read-only monitoring of attendance |
| Platoon Leader | Own company and platoon | Add and edit cadets, take and submit attendance |
| Battalion S1 (2 accounts) | All cadets | Review roster, approve attendance, edit cadet data |
| Brigade S1 (1 account) | All cadets | Review roster, approve attendance, edit cadet data |

> The system allows exactly **two Battalion S1 accounts** and **one Brigade S1 account**. Because Battalion S1 has no battalion field at registration, all three S1 accounts have the same data scope. Battalion S1 and Brigade S1 are both required approvers for attendance, but they can approve in any order.

## 2. Authentication and Registration

### 2.1 Log In
- Form with username and password.
- Below the form: "Don't have an account? **Register**" linking to the registration form.
- Failed logins are rate limited (temporary lockout after repeated failures).
- Sessions expire after a period of inactivity.
- "Forgot password" flow (see 2.5).
- A user with a temporary password or a first-login Admin account is sent to a **Change password** page before anything else.

### 2.2 Registration
Fields:
- First name, middle name, last name
- Student number (used by the Admin to verify identity)
- Email
- Password (must meet the password policy in section 6)
- Role: Class President, Platoon Leader, Battalion S1, or Brigade S1
- Consent checkbox for the Data Privacy Notice

Not entered by the user: **username and user ID.** Both are generated by the system (see 2.3).

Conditional fields:
- **Class President:** a required **Program** dropdown from a controlled list (for example BSIT or BSCE). The program is the Class President's section. No year level.
- **Platoon Leader:** a **Company** dropdown (Alpha, Bravo, and so on) appears, then a **Platoon** dropdown filtered by that company (Alpha 1st, Alpha 2nd, and so on).
- **Battalion S1 and Brigade S1:** no extra fields.

Rules:
- Only one active Platoon Leader per platoon and one active Class President per program. If a conflict exists, the Admin sees a warning at review time.
- Only **two** active Battalion S1 accounts and **one** active Brigade S1 account are allowed. If the limit is already reached, the Admin cannot approve another registration for that role until an existing account is deactivated.
- Student number and email must be unique.

### 2.3 Generated Usernames and IDs
- The system generates a unique username when the registration is submitted, using the role code, year, and sequence number. Examples:
  - `PL-2026-0001` (Platoon Leader)
  - `CP-2026-0001` (Class President)
  - `BN-2026-0001` (Battalion S1)
  - `BR-2026-0001` (Brigade S1)
- The username is shown on the confirmation screen after registering, and is sent to the user's email when the account is approved. The user logs in with this username and the password they chose.
- If a rejected registration is edited and resubmitted, it keeps its original username.
- The Admin account is the only one with a fixed username, created at deployment (see 3.1).

### 2.4 Account Status
After submitting, the request goes to the Admin and the user returns to the log-in page. Logging in shows a message based on status:

| Status | Behavior |
|---|---|
| Pending | "Your registration is being processed." Login is blocked. |
| Approved | Login succeeds and the user lands on their role dashboard. |
| Rejected | Shows the Admin's reason. The user may edit the details and resubmit. |
| Deactivated | Login blocked (graduated, replaced, or removed). Reason shown to the user. |

### 2.5 Password Reset
- Users can request a reset by email.
- The Admin can also reset any user's password. A temporary password forces a change at next login.

## 3. Role Features

### 3.1 Admin
- **Account:** There is no registration for the Admin. The initial Admin account is created once at deployment by a setup script. The password is stored hashed, is not written in the source code, and must be changed at first login.
- **Registration requests:** Review pending requests, verify identity against the official roster, then approve or reject (a rejection reason is required).
- **User management:** Search users, change a user's role or assignment, deactivate or reactivate accounts, reset passwords.
- **Approver continuity:** There is only one Brigade S1 account, so if it is deactivated or unavailable, approvals are blocked. The Admin can approve a replacement account, and sessions waiting for approval stay in the queue for the new account holder.
- **Terms and training sessions:** Create terms (for example "1st Semester 2026-2027"). Only **one term is active** at a time. Create and manage the training calendar for the active term (date, label, status: scheduled, held, cancelled). The default is 15 sessions, but the count is configurable.
- **Structure setup:** Manage the lists of programs, companies, and platoons.
- **Settings:** Set the "at risk" attendance threshold (for example 80%).
- **Attendance:** View attendance for all cadets and export reports (same view as in 3.4).
- **Audit log:** View who changed what and when (see section 6).

### 3.2 Class President (read-only)
- Sees the list of cadets in their selected program (for example BSIT).
- Table columns: Full name (Last name, First name, Middle initial), Company, Platoon, and the training days (one column per session) showing the **fully approved** status: Present, Absent, Late, Excused, or blank if not yet recorded.
- Shows an attendance percentage per cadet (see 3.5).
- Cannot see sensitive personal data (birthday, email, contact number) and cannot edit anything.

### 3.3 Platoon Leader
Company and platoon are taken from the leader's account and applied automatically.

**Input Cadet**
- Manually enter: last name, first name, middle name, birthday, program, gender, student number, email, contact number.
- Company and platoon are auto-filled from the leader's assignment.
- The system generates a unique cadet ID (for example, `CDT-2026-0001`).
- Student number and email must be unique. Duplicates are blocked with a clear message.
- **Bulk import** from a CSV template is available, with a preview and error report before saving.

**View and Edit Cadet**
- Shows only cadets in the leader's own platoon.
- The leader can edit cadet information in this section.
- The leader **cannot change** a cadet's platoon or company. The leader can only **remove** a cadet from their own platoon. The cadet then shows as **Unassigned**, and only a Battalion S1 or Brigade S1 can assign them to a platoon and company. Their past attendance is kept.
- Cadets are never permanently deleted. Their status is marked instead (active, dropped, transferred, graduated, unassigned).

**Take Attendance**
- A session selector above the table lists the training sessions, each with a status badge: Not started, Draft, Submitted, Returned, or Approved. This is how the leader tracks the progress of their own submissions.
- The table is similar to View Cadet but shows only Last name, First name, Middle initial, and Program, with one column per training session (date). Each session column has its own **Submit** button.
- Only the current or past sessions can be marked. Future sessions are locked.
- Each cadet has a status selector: **P** Present, **A** Absent, **L** Late, **E** Excused.
  - **L** optionally records minutes late.
  - **E** requires a reason, with an optional attached document (documents are added in Phase 3).
- Cadets start as **Not yet marked** (blank), never defaulted to Absent.
- A **Mark all Present** shortcut lets the leader then change the exceptions.
- Draft entries are auto-saved so work is not lost.
- **Submit** sends that session's attendance to **both** the Battalion S1 and Brigade S1 for approval. All cadets must be marked before a session can be submitted.
- **Editing after submission:** the leader can edit a submitted session until it is fully approved. Any edit **clears approvals already given** and notifies both S1s, so they review the updated version. Once fully approved, the session is locked.
- The interface must work well on mobile.

### 3.4 Battalion S1 and Brigade S1
After Admin approval, both roles have the same roster and viewing features and cover all cadets. Attendance needs approval from **one Battalion S1 and the Brigade S1**.

**View and Edit Cadet Roster**
- Shows every cadet's information in the database (no attendance in this view).
- Can edit all fields.
- Can assign unassigned cadets and move cadets between platoons and companies. This is the only place a cadet's platoon or company can be changed.
- Filters: gender, program, company, platoon, and cadet status.
- Search and pagination for large rosters.

**Review and Approve Attendance**
- Submitted sessions appear in a queue with the platoon, session date, and counts.
- A session needs two approvals before it is recorded: **one of the two Battalion S1 accounts** and the **Brigade S1**. Either approval can come first.
- Once one Battalion S1 approves, the other Battalion S1 sees the session as "Already approved by Battalion S1" and has nothing left to do on it.
- Any of the three S1 accounts can **Return** the submission with remarks. A returned session goes back to the Platoon Leader and all approvals are cleared.
- Attendance is only recorded in the official records after both approvals are in.

**View Attendance**
- A roster table with Full name, Program, Company, and Platoon.
- One column per training session showing the status (P, A, L, E).
- At the bottom of each column, a summary of total Present, Absent, Late, and Excused.
- Per-cadet attendance percentage, with an "at risk" highlight based on the Admin's threshold.
- Filters by company, platoon, program, and session.
- **Export** to CSV and PDF.

### 3.5 Attendance Percentage
Proposed default formula, shown on the Class President, Platoon Leader, and S1 views:

```
Attendance % = (Present + Late) ÷ (Approved sessions held − Excused) × 100
```

- A session counts as "held" only when it has been fully approved. Cancelled sessions and sessions not yet approved are never counted.
- Excused sessions are removed from the total, so they do not lower the percentage.
- If the denominator is zero, the percentage shows "—".
- The "at risk" threshold (for example below 80%) is set by the Admin in Settings. The exact rule should follow the ROTC unit's own policy.

## 4. Attendance Workflow

```
Draft → Submitted → Battalion S1 approved (either of 2) ─┐
                  → Brigade S1 approved                 ──┴→ Approved (locked)

Any S1 can Return → back to Platoon Leader (all approvals cleared)
Platoon Leader edit after submit → approvals cleared, S1s notified
```

| State | Who | Description |
|---|---|---|
| Draft | Platoon Leader | Being edited. Not visible to S1. |
| Submitted | Platoon Leader | Sent to both S1s. Can still be edited by the leader. |
| Partially approved | S1 | Either the Battalion S1 level or the Brigade S1 has approved, but not both. |
| Returned | S1 | Sent back with remarks. The leader corrects and resubmits. |
| Approved | Battalion S1 and Brigade S1 | Recorded in official records, locked, and visible to the Class President. |

Rules:
- Submission is **per training session**, not all 15 days at once.
- Approved records are locked. Later corrections require a documented S1 override, and both the old and new values are logged. The override screen is built in Phase 3.
- Only fully approved attendance counts in summaries, percentages, and the Class President view.
- Notifications go to the S1s on submission or edits, and to the Platoon Leader on approval or return.

## 5. Data Model (Summary)

| Entity | Key Fields |
|---|---|
| User | id, generated username, password hash, names, student number, email, role, status, rejection reason, must change password |
| Assignment | user, program (Class President), company and platoon (Platoon Leader) |
| Program, Company, Platoon | Controlled lists. A platoon belongs to a company. |
| Term | id, name, start date, end date, is active (only one active at a time) |
| Cadet | id, names, birthday, gender, program (links to the Program list), student number, email, contact number, status |
| Enrollment | cadet, term, company (nullable), platoon (nullable). Empty values mean the cadet is Unassigned. Keeps history across semesters and transfers. |
| TrainingSession | id, term, date, label, status |
| AttendanceRecord | cadet, session, status (P/A/L/E), minutes late, excuse reason, document |
| AttendanceSubmission | platoon, session, state, submitted by, battalion approval, brigade approval, remarks, timestamps |
| Notification | user, message, link, is read, created at |
| Setting | key, value (for example the at-risk threshold) |
| AuditLog | actor, action, entity, old value, new value, timestamp |

Notes:
- Training days are records in the database, not hardcoded columns.
- Gender, program, company, and platoon are controlled lists.
- Use soft deletes.

## 6. Security and Privacy

**Security**
- Passwords are hashed with bcrypt or argon2, with a minimum policy (for example, at least 10 characters with mixed character types).
- Rate limiting and lockout on login. Session timeout.
- Role and scope are enforced **on the server** for every request, not just hidden in the UI.
- No credentials stored in source code.
- Audit log records account approvals, role changes, cadet edits, platoon removals and moves, attendance edits, approvals, overrides, and exports.

**Privacy**
- The system stores personal data (birthday, email, contact number), so the Philippine Data Privacy Act (RA 10173) applies.
- Collect only what is needed, and show personal details only to roles that require them.
- A consent notice is shown at registration.
- Define a data retention period for records of graduated cadets.

## 7. Notifications

In-app notifications (shown in the bell dropdown) for:
- Account approved, rejected, or deactivated
- Attendance submitted or edited (to both S1s), and approved or returned (to the Platoon Leader)

Email is sent for: the generated username on account approval, and password reset links.

---

## 8. Non-Functional Requirements

- Mobile-friendly, since leaders will take attendance on phones.
- Search, pagination, and fast loading for rosters in the hundreds.
- Daily backups of the database.
- Clear error and empty-state messages.
- An email service (for example SMTP) is required for usernames and password resets. In local development, emails are written to a log and to the notifications table instead (see `RULES.md`).

---

## 9. Suggested Build Phases

1. **MVP:** Log in, registration with generated usernames, Admin approval, cadet input and view, take and submit attendance, two-level S1 approval, view attendance.
2. **Phase 2:** Filters and exports, attendance percentages, bulk import, notifications.
3. **Phase 3:** Audit log viewer, excuse documents, S1 override of approved records and correction requests, analytics.
